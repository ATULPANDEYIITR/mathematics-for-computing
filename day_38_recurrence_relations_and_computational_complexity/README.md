# Recurrence Relations and Computational Complexity

## Scope

This repository presents two closely connected areas of algorithm analysis.

The first is **recurrence relations**, which express the running time of recursive algorithms in terms of the running time of smaller instances. The second is **computational complexity theory**, which studies how the resources required by algorithms grow with input size and how decision problems relate to classes such as P and NP.

The implementations deliberately distinguish four ideas that are often mixed together:

- A **recurrence relation** describes the growth of an algorithm whose execution is defined recursively.
- **P** concerns decision problems solvable by deterministic algorithms in polynomial time.
- **NP** concerns decision problems for which a proposed solution, called a certificate, can be verified in polynomial time.
- **NP-completeness** requires both membership in NP and NP-hardness under an appropriate polynomial-time reduction.

The examples use SAT, 3-SAT, CLIQUE, and SUBSET SUM because these problems make the distinction between finding a solution, verifying a solution, and transforming one problem into another particularly clear.

---

## Recurrence Relations

A recurrence relation defines a quantity using smaller instances of itself.

For an algorithm, the quantity is usually its running time. A simple recursive factorial implementation has the structure

`T(n) = T(n - 1) + Θ(1)`

because one recursive call processes `n - 1`, while the multiplication and surrounding operations take constant time. Expanding the recurrence produces a linear number of levels, giving `Θ(n)` time.

The Python, JavaScript, C++, and Java implementations all include recursive and iterative Fibonacci calculations. Fibonacci is more useful as a complexity example because naive recursion creates overlapping subproblems:

`T(n) = T(n - 1) + T(n - 2) + Θ(1)`

The same smaller Fibonacci values are recomputed many times. The number of recursive calls therefore grows exponentially.

Memoization changes the behavior by storing results that have already been calculated. Each Fibonacci state from `0` through `n` is computed once, producing `O(n)` time at the cost of `O(n)` additional storage.

The iterative implementation removes the recursive call stack and keeps only the two preceding Fibonacci values, giving `O(n)` time and `O(1)` auxiliary space.

The important distinction is that the mathematical recurrence describes the computation generated by an algorithm. Changing the algorithm can change the recurrence and therefore change the complexity.

---

## Divide-and-Conquer Recurrences

A common divide-and-conquer recurrence has the form

`T(n) = aT(n/b) + f(n)`

where:

- `a` is the number of recursive subproblems,
- `n/b` is the approximate size of each subproblem,
- `f(n)` is the non-recursive work performed at the current level.

Merge sort provides the standard example:

`T(n) = 2T(n/2) + Θ(n)`

Two half-sized problems are solved recursively and the two sorted sequences are merged in linear time.

The Python implementation includes a recurrence-tree calculation that exposes the work performed at each level. For merge sort, each level contributes approximately linear total work, and there are logarithmically many levels. The resulting bound is `Θ(n log n)`.

Binary search has a different recurrence:

`T(n) = T(n/2) + Θ(1)`

Only one half of the search space remains after each comparison. The number of levels is logarithmic, giving `Θ(log n)`.

---

## Master Theorem

For recurrences of the form

`T(n) = aT(n/b) + Θ(n^c)`

the comparison between `c` and `log_b(a)` determines the dominant source of work in the standard polynomial cases.

When `c < log_b(a)`, the recursive subproblems dominate.

When `c = log_b(a)`, the work is balanced across the recurrence tree and a logarithmic factor appears.

When `c > log_b(a)`, the work performed outside the recursive calls dominates, subject to the usual regularity conditions of the theorem.

The Python implementation includes an executable `master_theorem` function that evaluates these polynomial cases rather than presenting the theorem only as prose.

This classification should not be treated as a universal solver for every recurrence. Recurrences containing irregular subproblem sizes, non-polynomial terms, unusual additive components, or dependencies outside the Master Theorem's assumptions require other techniques.

## Asymptotic Complexity

Asymptotic analysis focuses on how resource usage grows as the input size becomes large.

The implementations contrast representative growth rates:

| Growth | Typical interpretation |
|---|---|
| `O(1)` | Resource usage does not depend materially on input size |
| `O(log n)` | Each operation substantially reduces the remaining search space |
| `O(n)` | One pass over the input is sufficient |
| `O(n log n)` | Common in efficient comparison-based divide-and-conquer algorithms |
| `O(n²)` | Pairwise relationships or nested scans often produce this growth |
| `O(2^n)` | Exhaustive Boolean assignment or subset enumeration can produce this growth |

The distinction between an asymptotic upper bound and an exact execution time is important. Big-O notation does not predict wall-clock seconds. It describes a growth relationship while abstracting away machine-specific constants and lower-order terms.

## Decision Problems

Complexity classes such as P and NP are conventionally defined for **decision problems**.

A decision problem asks a question with a yes-or-no answer.

For example:

`Does this Boolean formula have a satisfying assignment?`

`Does this graph contain a clique of size at least k?`

`Does this collection contain a subset whose values sum to the target?`

The distinction matters because complexity-class definitions are based on decision versions of computational problems.

A search problem may ask for the actual satisfying assignment or the actual clique. A decision version asks only whether such an object exists.

The implementations frequently use a search procedure to discover a certificate because that makes the computational contrast visible, but the theoretical classification is applied to the corresponding decision problem.

---

## P

**P** contains decision problems that have deterministic algorithms whose running time is polynomial in the input size.

Examples include many graph reachability and shortest-path decision problems.

The implementations use binary search and other polynomial-time algorithms to provide concrete examples of algorithmic behavior that remains within polynomial growth.

Membership in P is about the existence of a polynomial-time algorithm. A particular inefficient implementation does not prove that a problem is outside P.

This distinction is important when interpreting brute-force demonstrations. An exhaustive algorithm may take exponential time even for a problem that has a polynomial-time solution. The complexity classification concerns the best polynomial-time algorithm known to exist, not the worst implementation someone happens to write.

---

## NP

**NP** contains decision problems for which a proposed yes-answer can be verified in polynomial time by a deterministic verifier.

The proposed solution is commonly called a **certificate**.

For SAT, the certificate is a Boolean assignment. The verifier evaluates the formula under that assignment and checks whether every clause is satisfied.

For CLIQUE, the certificate is a set of vertices. The verifier checks that the vertices exist and that every pair is connected by an edge.

For SUBSET SUM, the certificate is a collection of input positions. The verifier checks that the positions are valid and that their values sum to the target.

The verification procedures in the implementations are intentionally separate from the search procedures. This exposes the central NP distinction:

**A certificate can be easy to verify even when discovering a certificate is computationally difficult.**

---

## SAT Certificate Verification

The SAT model represents a formula in conjunctive normal form.

A CNF formula is an AND of clauses, while each clause is an OR of literals.

For example, a clause can contain literals such as:

`x`

`¬y`

`z`

A Boolean assignment gives each variable a truth value.

A clause is satisfied when at least one of its literals evaluates to true. The entire CNF formula is satisfied only when every clause is satisfied.

The Python, JavaScript, C++, and Java implementations explicitly represent variables, literals, clauses, and assignments. The SQL implementation stores them in normalized relational tables and evaluates a certificate using aggregation.

The important computational property is that checking every clause and its literals requires work polynomial in the explicit representation of the formula.

---

## NP-Completeness

A decision problem is **NP-complete** when two conditions hold:

1. The problem belongs to NP.
2. The problem is NP-hard under polynomial-time reductions.

SAT is the canonical NP-complete problem established by the Cook-Levin theorem.

3-SAT is a restricted SAT formulation in which each clause contains exactly three literals. It remains NP-complete.

CLIQUE and SUBSET SUM are also standard NP-complete problems.

The implementations do not claim that a brute-force solver makes a problem NP-complete. Brute force only demonstrates one possible algorithmic strategy.

The classification requires a proof involving both efficient certificate verification and reductions.

---

## NP-Hardness

A problem is NP-hard when every problem in NP can be transformed to it using the relevant polynomial-time reduction notion.

An NP-hard problem does not necessarily need to belong to NP.

This is why NP-hard and NP-complete are not interchangeable terms.

If a problem is both NP-hard and in NP, it is NP-complete.

The reduction examples in this repository focus on decision problems and use the standard polynomial-time reduction relationship.

---

## Polynomial-Time Reductions

A polynomial-time reduction transforms an instance of one problem into an instance of another problem within polynomial time while preserving the yes/no answer.

The notation

`A ≤p B`

means that instances of A can be transformed into instances of B in polynomial time such that the transformed instance has the required answer exactly when the original instance does.

The direction is critical.

If

`A ≤p B`

and B has a polynomial-time algorithm, then A can also be solved in polynomial time:

`A instance → polynomial transformation → B instance → polynomial B algorithm`

This is why reductions are central to NP-hardness proofs.

A reduction does not mean that the two problems have identical structure. It means that solving the target problem efficiently would provide an efficient way to solve the source problem.

---

## 3-SAT to CLIQUE Reduction

The C++, JavaScript, Java, Python, and SQL implementations model the classic reduction from 3-SAT to CLIQUE.

Suppose the source formula has clauses

`C1, C2, ..., Cm`

Each literal occurrence becomes a vertex in the target graph.

For every pair of literal occurrences belonging to different clauses, an edge is created unless the literals contradict one another.

Two literals contradict when they refer to the same variable but have opposite signs.

For example:

`x`

and

`¬x`

cannot simultaneously represent true literals under one consistent assignment, so their corresponding vertices are not connected.

Vertices from the same clause are also not connected because a target clique must select at most one literal from each clause.

The target CLIQUE instance asks whether the graph contains a clique of size `m`, where `m` is the number of source clauses.

A clique of that size must select one vertex from every clause and every selected pair must be mutually compatible.

Those selected literals therefore correspond to a consistent set of choices that satisfies all clauses.

The reduction is polynomial because a 3-SAT formula with `m` clauses creates exactly three literal-occurrence vertices per clause, giving `3m` vertices. Constructing and examining pairs of vertices requires polynomial work.

---

## Why the Reduction Direction Matters

The statement

`3-SAT ≤p CLIQUE`

means that 3-SAT is transformed into CLIQUE.

It does **not** mean that CLIQUE is transformed into 3-SAT by the same construction.

The practical consequence is:

If CLIQUE had a polynomial-time algorithm, the transformation could be applied first and the resulting CLIQUE instance could then be solved efficiently. This would produce a polynomial-time algorithm for 3-SAT.

Because 3-SAT is NP-complete, such an algorithm would have major consequences for the relationship between P and NP.

---

## P versus NP

The central unresolved question is whether

`P = NP`

The implementations intentionally do not claim that P and NP are known to be different.

The established facts used by the examples are:

- `P ⊆ NP`
- SAT is in NP.
- SAT is NP-complete.
- 3-SAT is NP-complete.
- CLIQUE is NP-complete.
- SUBSET SUM is NP-complete.
- Polynomial reductions can transfer algorithmic consequences between problems.

If any NP-complete decision problem were shown to have a polynomial-time algorithm, then every problem in NP would have a polynomial-time algorithm, implying `P = NP`.

If `P ≠ NP`, then no NP-complete problem can have a polynomial-time algorithm.

The implementations therefore distinguish proven classifications from experimental execution behavior.

## Brute-Force Search Versus Verification

The SAT search implementations enumerate Boolean assignments.

With `n` Boolean variables, there are

`2^n`

possible assignments.

This produces a rapidly growing search space:

| Variables | Assignments |
|---:|---:|
| 5 | 32 |
| 10 | 1,024 |
| 15 | 32,768 |
| 20 | 1,048,576 |
| 30 | 1,073,741,824 |

The exact runtime of an implementation depends on hardware, representation, compiler behavior, interpreter behavior, and early termination. The important theoretical observation is the exponential number of candidate certificates.

Verification is fundamentally different.

Once a certificate is supplied, SAT verification evaluates the supplied assignment against the formula rather than enumerating all possible assignments.

This difference is one of the main reasons NP is defined through efficient verification.

---

## CLIQUE Verification

A CLIQUE certificate consists of a set of vertices.

For a proposed clique containing `k` vertices, the verifier checks every pair.

There are

`k(k - 1) / 2`

unordered vertex pairs.

With an appropriate adjacency representation, each pair can be checked efficiently. The resulting verification process is polynomial in the explicit input and certificate size.

The implementation rejects certificates containing:

- nonexistent vertices,
- duplicate vertices,
- non-adjacent pairs.

The C++ and Java implementations model the graph explicitly, while the JavaScript implementation uses a `Set` of normalized edge identifiers.

---

## SUBSET SUM Verification

For SUBSET SUM, the certificate identifies which input values are selected.

The verifier checks:

- every selected position is valid,
- no position is repeated,
- the selected values sum to the target.

The search implementation can enumerate subsets, creating up to `2^n` candidate subsets.

The certificate verifier does not need to examine every possible subset. It evaluates only the supplied candidate.

This is another direct example of the difference between finding a solution and verifying one.

---

## Python Implementation

The Python program is the broadest executable treatment of the topic.

It contains recurrence evaluators, recursive and memoized Fibonacci implementations, iterative algorithms, recurrence-tree calculations, Master Theorem classification for common polynomial cases, binary search, merge sort, SAT representation, SAT certificate verification, CLIQUE verification, SUBSET SUM search and verification, and a complete 3-SAT-to-CLIQUE construction.

The Python data model uses `dataclass` types for literals, clauses, formulas, graphs, and reduction metadata. This keeps mathematical entities explicit rather than hiding them inside unrelated dictionaries.

The reduction creates one graph vertex for each literal occurrence, records the originating clause, and adds compatibility edges only between non-contradictory literals from different clauses.

The Python program also separates exhaustive search from verification. `brute_force_sat` searches the candidate space, while `verify_sat_certificate` checks an already supplied assignment.

This separation is intentional because search complexity and verification complexity are not the same concept.

---

## JavaScript Implementation

The JavaScript program takes a different implementation perspective.

It uses classes and immutable objects for literals, clauses, formulas, and graphs. The SAT search uses a generator to enumerate assignments without constructing the complete list of assignments in memory.

The generator does not make the search polynomial. It changes the memory behavior of enumeration while the number of possible assignments remains exponential.

The JavaScript implementation also includes an event-driven verification service. Verification emits `evaluationStarted` and `evaluationCompleted` events and uses a Promise-based execution boundary.

This models a realistic application architecture in which computational verification can be integrated into an event-driven service without confusing asynchronous programming with computational complexity. Making an operation asynchronous does not change an exponential algorithm into a polynomial one.

The 3-SAT-to-CLIQUE transformation is implemented separately from the SAT solver, preserving the direction and structure of the reduction.

---

## C++ Case Study

The C++ program treats complexity analysis as a small computational-governance engine.

The implementation contains explicit domain objects for:

- literals,
- clauses,
- CNF formulas,
- graphs,
- graph metadata,
- reductions,
- decision-problem classifications.

The graph uses sets of normalized vertex pairs for deterministic edge representation. The CLIQUE verifier checks all pairs of selected vertices.

The 3-SAT-to-CLIQUE reduction records the clause associated with every target vertex. It creates edges only when two literal occurrences come from different clauses and are not contradictory.

A recursive combination search then attempts to find a target clique. The search is deliberately separate from the verifier. The verifier accepts or rejects a proposed clique without searching for one.

The program also models P, NP, NP-hard, and NP-complete as distinct classifications. This prevents the common mistake of treating NP as synonymous with NP-complete.

## Java Enterprise Model

The Java implementation uses explicit domain abstractions suitable for a larger service-oriented system.

`DecisionProblem` records the problem classification and certificate policy.

`Certificate` defines the common concept of a proposed witness.

`SATCertificate` and `CliqueCertificate` represent problem-specific certificate types.

`CertificateVerifier` provides a generic verification abstraction, while `VerificationService` exposes domain-specific verification behavior.

The use of records makes immutable mathematical data natural. Lists and maps are defensively copied so that a certificate cannot unexpectedly change after being accepted by a verification service.

The Java model also represents the 3-SAT-to-CLIQUE transformation with `LiteralOccurrence` and `CliqueReduction`, making the source-clause relationship explicit.

This structure is more appropriate for an enterprise system than embedding all logic in a single sequence of print statements.

## SQL Data Model

The PostgreSQL implementation treats complexity experiments as relational data.

`decision_problem` stores problem classifications and certificate descriptions.

`recurrence_relation` stores recurrence expressions, base cases, asymptotic bounds, and interpretations.

`polynomial_reduction` records the direction of reductions and the claimed transformation properties.

The SAT model is normalized across:

- `sat_instance`
- `sat_variable`
- `sat_clause`
- `sat_literal`
- `sat_certificate`
- `sat_certificate_assignment`

This structure represents the relationship between variables, clauses, literal occurrences, and certificates instead of storing a formula as an opaque string.

The CLIQUE model uses:

- `clique_instance`
- `graph_vertex`
- `graph_edge`
- `clique_certificate`
- `clique_certificate_vertex`

The graph construction query implements the same compatibility rule used by the programmatic reductions.

SUBSET SUM is represented through an instance table, input values, certificate, and selected values. A query then computes the certificate sum and compares it with the target.

---

## Database-Level Integrity

The SQL implementation uses primary keys and foreign keys to prevent orphaned entities.

`CHECK` constraints prevent invalid values such as non-positive positions and invalid required clique sizes.

Unique constraints prevent duplicate variable names within an instance, duplicate clause positions, duplicate literal positions, and duplicate certificate names.

Indexes are placed on fields used to connect or locate graph and SAT data. These indexes do not change the theoretical complexity class of the underlying decision problem. They improve access paths for the database workload.

The database deliberately does not attempt to express every semantic property through simple constraints. For example, whether an entire SAT formula is satisfied by a certificate requires evaluating relationships across multiple tables. That is represented as a query.

This distinction mirrors application architecture: structural integrity belongs in constraints, while multi-row semantic evaluation can belong in queries or procedures.

---

## Transactional Behavior

The SQL script changes one SAT certificate assignment inside a transaction and then evaluates the formula.

The transaction ends with `ROLLBACK`, so the experimental mutation does not permanently change the stored certificate.

This demonstrates a database-specific concern that is different from computational complexity itself.

A transaction controls the atomicity and persistence of database operations. It does not alter the asymptotic complexity of SAT verification.

Similarly, an index can make a particular database query substantially faster without changing an NP-complete problem into a P problem.

## Edge Cases

### Recurrence evaluation

Recursive algorithms can fail because of negative input, excessive recursion depth, or integer overflow.

Memoization avoids repeated computation but requires additional memory.

An iterative implementation can remove recursion overhead, but it may still have the same asymptotic time complexity as the memoized version.

### SAT

A verifier must reject assignments that omit variables or contain unexpected variables.

A malformed clause representation can also invalidate assumptions made by a reduction. The 3-SAT-to-CLIQUE construction therefore checks that every source clause contains exactly three literals.

### CLIQUE

A proposed certificate containing duplicate vertices is invalid.

A vertex outside the graph is invalid.

A set of vertices is not a clique merely because every vertex exists. Every pair must be connected.

### SUBSET SUM

Repeated certificate indices must be rejected because they could otherwise count one input value multiple times.

Invalid indices must be rejected before accessing input data.

The certificate sum must be compared with the target exactly according to the numeric representation being used.

### Reductions

A reduction must preserve yes/no answers.

Constructing a graph that merely resembles a source problem is not sufficient. The transformation requires a correctness argument connecting source solutions with target solutions.

## Common Conceptual Errors

**NP does not mean "non-polynomial."**

NP refers to polynomial-time verification of certificates for decision problems under the standard deterministic verifier formulation.

**NP does not mean "problems that require exponential time."**

Some problems in NP are already in P.

**NP-complete does not mean "the hardest problem imaginable."**

NP-complete problems are the hardest problems within NP under the relevant polynomial-time reduction framework.

**A brute-force implementation does not prove NP-completeness.**

It only demonstrates one algorithm for solving a problem.

**A polynomial reduction is not the same as a polynomial-time solution.**

The reduction transforms one problem into another. It does not itself necessarily solve the source problem.

**The direction of a reduction matters.**

`A ≤p B` says that A can be transformed into B. Reversing the direction requires a separate construction.

**Verification is not search.**

The fact that a certificate can be checked efficiently does not imply that the certificate can be found efficiently.

## Performance Considerations

Recurrence analysis should identify where work originates.

For naive Fibonacci, the major issue is repeated computation.

For merge sort, the work is distributed across logarithmically many recursion levels, with linear total work per level.

For binary search, each comparison eliminates approximately half the remaining candidates.

For SAT, CLIQUE, and SUBSET SUM, brute-force search can produce exponential candidate spaces.

The implementations use small instances when exhaustive search is required. This is intentional because a demonstration of exponential growth should not attempt to enumerate impractically large spaces merely to make the program appear more comprehensive.

The number of possible certificates can grow exponentially even when checking one supplied certificate remains polynomial.

---

## Security and Correctness Considerations

Complexity classification is not a security guarantee.

An NP-complete problem can still be implemented incorrectly, accept malformed certificates, suffer integer overflow, or expose denial-of-service behavior through uncontrolled input sizes.

Production systems should therefore validate:

- input size,
- certificate structure,
- numeric ranges,
- graph membership,
- duplicate identifiers,
- malformed formulas,
- resource limits.

A brute-force verifier exposed through an unrestricted API can become a resource-exhaustion vulnerability. The implementation should distinguish a polynomial certificate verifier from an exponential certificate search service.

Polynomial-time does not automatically mean inexpensive. A high-degree polynomial can still be operationally expensive at scale.

Likewise, an algorithm with an excellent asymptotic bound can perform poorly on small inputs because of constants, memory access patterns, serialization, or implementation overhead.

---

## Relationship Between the Main Concepts

The concepts form a logical chain without being interchangeable.

A recursive algorithm may be analyzed using a recurrence relation.

The resulting running-time bound may be polynomial, logarithmic, linearithmic, or exponential.

Complexity theory then asks broader questions about the existence of efficient algorithms for decision problems.

P captures problems with polynomial-time decision algorithms.

NP captures problems with polynomial-time certificate verification.

Reductions compare the computational difficulty of problems.

NP-hardness uses reductions to establish that a problem is at least as difficult as every problem in NP under the selected reduction model.

NP-completeness combines NP membership with NP-hardness.

The 3-SAT-to-CLIQUE construction connects these ideas concretely:

`3-SAT instance`
→ `polynomial transformation`
→ `CLIQUE instance`
→ `candidate clique`
→ `polynomial verification`

The transformation explains why an efficient general solver for CLIQUE would have consequences for 3-SAT.

That is the central distinction maintained throughout these implementations: recurrence analysis studies the growth of particular computations, while P, NP, NP-hardness, NP-completeness, and reductions study relationships among computational problems.
